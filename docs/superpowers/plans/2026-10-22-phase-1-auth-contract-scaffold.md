# Phase 1: Auth, Contract, Scaffold Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A field user signs in to Procore from the iPhone app, picks a company and project, and sees that project's RFI list served by our Go backend; the OpenAPI contract generates both the Go server and the Swift client in CI.

**Architecture:** One repo with `api/` (Go, chi, oapi-codegen strict server, sqlc, Postgres) and `ios/` (SwiftUI, XcodeGen project, `FieldAssistantAPI` package generated by swift-openapi-generator from a copy of `api/openapi.yaml`). The backend is the Procore OAuth client and holds refresh tokens encrypted at rest; the phone holds only our session tokens in Keychain. No LLM, drafts, jobs or attachments in this phase.

**Tech Stack:** Go 1.24, `github.com/go-chi/chi/v5`, `github.com/oapi-codegen/oapi-codegen/v2` (strict server), `github.com/jackc/pgx/v5`, `github.com/sqlc-dev/sqlc`, `github.com/golang-migrate/migrate/v4`, `github.com/golang-jwt/jwt/v5`, `golang.org/x/sync/singleflight`, Postgres 16; Swift 6, iOS 17, XcodeGen, `swift-openapi-generator` + `swift-openapi-urlsession`, XCTest; Docker Compose, Caddy, GitHub Actions.

**Spec:** `procore-field-assistant-spec.md` (sections: Authentication and authorization, Backend spec, iOS app spec, Hosting) as amended by `docs/superpowers/specs/2026-10-22-v1-decisions.md`.

## Global Constraints

- Go `1.24` in `api/go.mod`; Swift tools version `6.0`; iOS deployment target `17.0`.
- The Go module root is `api/`, never the repo root. The Xcode project is generated from `ios/project.yml`; `ios/*.xcodeproj` is gitignored.
- `api/openapi.yaml` is the only contract. `ios/Packages/FieldAssistantAPI/Sources/FieldAssistantAPI/openapi.yaml` is a byte-for-byte copy maintained by `make sync-contract`; CI fails if they differ.
- Every API path is under `/v1` except `GET /healthz`.
- Session access JWT lifetime `15m`; refresh token lifetime `30d`, rotated on every use; a reused refresh token deletes the whole session.
- Procore refresh and access tokens are stored AES-256-GCM encrypted with the key from env `TOKEN_VAULT_KEY` (32 bytes, base64).
- Procore `client_secret`, `TOKEN_VAULT_KEY`, `SESSION_SECRET` come only from the environment; `.env` is gitignored; `.env.example` lists every variable with a placeholder.
- Every Procore REST request except `/oauth/*` and `GET /rest/v1.0/companies` carries header `Procore-Company-Id`.
- Procore base URLs come from config: `PROCORE_LOGIN_URL` (`https://login-sandbox.procore.com` in dev, `https://login.procore.com` in prod) and `PROCORE_API_URL` (`https://sandbox.procore.com` / `https://api.procore.com`).
- Error responses are always `{"code": string, "message": string}` with codes from: `bad_request`, `unauthorized`, `reauth_required`, `forbidden_scope`, `procore_permission_denied`, `not_found`, `procore_unavailable`, `internal`.
- Deep link scheme is `fieldassistant`; callback target is `fieldassistant://auth?code=<one-time code>`.
- Sign-in is PKCE-bound: the client sends `code_challenge` to `/auth/start` and `code_verifier` to `/auth/exchange`; the backend rejects a mismatch. (Added during execution after a security review.)
- Bundle identifier `com.monroeresidential.fieldassistant` (placeholder until the spec's open question is answered; it is set in exactly one place, `ios/project.yml`).
- Commit after every task with the message given in the task.

## Review Focus

1. **Procore revokes the refresh token** (user changed password). Any `/v1` call that needs Procore must return `401 {"code":"reauth_required"}` and mark `users.reauth_required = true`; the app shows one sign-in prompt and must not loop. Test in Task 9 (`TestTokenSource_RefreshRevoked_MarksReauth`) and Task 15 (`testRefreshFailureClearsSessionOnce`).
2. **A refresh token is replayed** (stolen or a retried request after rotation). The second use must delete the session so neither token works again. Test in Task 6 (`TestSessions_RefreshReuse_RevokesFamily`).
3. **Procore returns 429** on a list call. The client must wait and retry, not surface an error to the user. Test in Task 8 (`TestClient_ListCompanies_RetriesOn429`).
4. **A project list spans more than one page** (Procore pages at 100). All pages must be returned. Test in Task 8 (`TestClient_ListProjects_FollowsPagination`).
5. **A user asks for a company they cannot see**. `/v1/companies/{id}/projects` must return `403 forbidden_scope`, never a Procore error leaked through. Test in Task 11 (`TestProjects_CompanyNotVisible_403`).

- Deliberately out of phase 1: `/projects/{id}/features` permission probing (milestone 4), lookups, drafts, jobs, attachments, LLM.
- Deviations from the spec, by design: callback redirects with a one-time `code` exchanged at `POST /auth/exchange` instead of carrying the session in the deep link (keeps tokens out of URLs and lets the web app later set a cookie from the same callback). `PUT /me/selection` added so "remembers the last choice per user" survives reinstalls.
