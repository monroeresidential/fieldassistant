# Procore Field Assistant — iOS App & Backend Project Spec

Oct 22, 2026 · Drew Friestedt

## Overview

Field Assistant is an iOS app and a desktop web app that let a superintendent or PM create Procore records by talking to their phone or computer. The first feature is RFIs: the user dictates the question, adds photos, reviews a prefilled form, and taps submit. Every later feature (daily logs, observations, punch items) follows the same four-step loop, so the product grows by adding one feature module at a time, not by redesigning.

**The loop every feature runs:**

1. **Capture** — voice (transcribed on device) plus photos, GPS and timestamp.
2. **Extract** — the backend sends the transcript to an LLM that fills the Procore schema for that record type, picking IDs (people, locations, spec sections) only from live Procore lookups.
3. **Review** — the app shows the prefilled form with uncertain fields flagged; the user corrects and confirms. Nothing is submitted without a tap.
4. **Submit** — the backend uploads attachments, posts the record to Procore, and logs transcript, payload and result for audit.

**Users:** Monroe Residential / 3F Construction field staff first (118 W Illinois, 223 W Erie site teams), then any Procore user if the app is published to the Procore Marketplace.

**Why a backend exists at all:** Procore's OAuth token exchange requires a `client_secret`, which cannot ship inside an iOS binary. The backend holds the Procore client credentials, the user's refresh tokens and the LLM API key; the app holds only a short-lived session token.

## Goals and non-goals

v1 is done when a field user can create a complete, correctly-assigned RFI with photos in under 60 seconds from the moment they open the app, without touching the Procore web UI.

**Goals**

- Sign in once with Procore; the app never asks for Procore credentials again until the refresh token is revoked.
- Dictate an RFI in plain language and get a Procore-valid draft with subject, question, assignee, location, due date, impacts and attachments prefilled.
- Never submit an invented ID: every person, location, spec section, cost code or vendor comes from a live Procore lookup.
- Work on a jobsite with poor signal: capture and transcription are on-device; submission queues and retries.
- Extend to new Procore record types by adding one feature module in each repo, with no changes to auth, capture, review or audit code.
- Full audit trail: transcript, LLM output, user edits, final payload and Procore response stored per submission.

**Non-goals for v1**

- Android and a native Mac app (the backend is platform-neutral; the web app covers desktop).
- Reading or responding to existing RFIs beyond a basic list.
- Fully automatic submission with no review step (deferred; see Open questions).
- Procore Marketplace listing (built so it is possible, not required for internal use).
- Replacing the Procore mobile app for anything other than record creation.

## Repository strategy

Three repos on GitHub, connected by one OpenAPI contract that lives in the backend repo and generates every client. Separate repos because the toolchains, CI, release cadence and hosting are different: the backend deploys continuously to DigitalOcean; the web app deploys on every merge to Cloudflare Pages; the iOS app ships through TestFlight and App Store review.

| Repo | Contents | Toolchain / CI | Hosting / releases |
| --- | --- | --- | --- |
| `field-assistant-api` (Go) | HTTP API, OAuth broker, Procore client, LLM service, job queue, Postgres migrations, `openapi.yaml` | Go 1.23+, `oapi-codegen`, Docker, GitHub Actions | DigitalOcean droplet; continuous; tagged `vX.Y.Z` when the contract changes |
| `field-assistant-ios` (Swift) | SwiftUI app, feature modules, generated API client package pinned by tag | Xcode 16+, Swift 6, `swift-openapi-generator`, Fastlane, Xcode Cloud or GitHub Actions | TestFlight per feature; App Store per milestone |
| `field-assistant-web` (TypeScript) | React desktop web app, feature modules, generated API client pinned by tag | Vite, React, TypeScript, `openapi-typescript`, Playwright, GitHub Actions | Cloudflare Pages; preview per PR, production on merge to `main` |

**The contract is the only coupling.** `openapi.yaml` in the backend repo is the source of truth. The backend generates its server interface from it (`oapi-codegen`), so a handler cannot drift from the spec. The iOS repo consumes the same file through a Swift package (`FieldAssistantAPI`) generated by `swift-openapi-generator`, and the web repo through `openapi-typescript` + `openapi-fetch`; both pin a backend release tag. CI on the backend fails if `openapi.yaml` changes without a version bump.

**Adding a feature touches both repos in a fixed order:**

1. Backend: add the feature's schemas and endpoints to `openapi.yaml`; bump the minor version.
2. Backend: implement the feature module (`internal/features/<name>`): Procore mapping, LLM extraction schema, submit job. Merge, tag, deploy.
3. iOS and web: bump the API package to the new tag; regenerate the clients.
4. iOS and web: add the feature module (`Features/<Name>` / `src/features/<name>`): capture config, review screen, field pickers. Ship to TestFlight and Cloudflare Pages.

**Versioning rule:** the backend supports the two most recent minor contract versions so an un-updated phone keeps working (the web app is always current, so it can use the newest). Breaking changes get a new major version and a new path prefix (`/v2`).

**Monorepo was considered and rejected:** Xcode projects inside a Go module tree complicate both `go` tooling and Xcode Cloud, and nothing is shared at the code level — only the contract, which a package dependency handles cleanly.

## Authentication and authorization

The backend is the OAuth client; the phone never holds a Procore token.

**Sign-in flow**

1. App calls `POST /auth/start` → backend returns a Procore authorize URL with a one-time `state` bound to the device.
2. App opens it in `ASWebAuthenticationSession`. User signs in to Procore (SSO, MFA — all Procore's).
3. Procore redirects to the backend's `GET /auth/callback` with `code`. Backend exchanges it at `login.procore.com/oauth/token` using `client_id` + `client_secret` (Authorization Code grant, [Procore docs](https://developers.procore.com/documentation/oauth-auth-grant-flow)).
4. Backend stores the refresh token encrypted (envelope encryption, key in the host's KMS or a sealed secret), creates or links an app user keyed on the Procore user ID, and issues a session JWT (15-minute access, 30-day refresh, rotated on use).
5. Backend redirects to `fieldassistant://auth?session=…`; `ASWebAuthenticationSession` hands it to the app, which stores the session in Keychain.

**Token lifecycle**

- Procore access tokens are refreshed server-side on demand with single-flight locking per user so concurrent jobs do not race the refresh.
- A failed refresh (revoked, password change) marks the user `reauth_required`; the app shows one sign-in prompt and resumes queued work after.
- Signing out revokes the Procore token via Procore's revoke endpoint and deletes the session.

**Company and project scope**

- After sign-in the backend lists `GET /rest/v1.0/companies` and `/projects`; the app shows a picker and remembers the last choice per user.
- Every Procore request carries `Procore-Company-Id`. The backend enforces that a session may only act on companies and projects the Procore user can see.

**Permissions**

- Creating an RFI requires Standard or Admin on the project's RFI tool. The backend surfaces Procore 403s as a specific error code (`procore_permission_denied` with the tool name) so the app can say exactly what is missing.
- Each feature module declares the Procore tools and permission levels it needs; the app greys out features the user cannot use on the selected project.

**Multi-tenant from day one.** Users, sessions, tokens and audit rows are keyed by Procore company ID so the same deployment can serve Monroe/3F and, later, Marketplace customers.

## Feature framework

A feature is a Procore record type plugged into a shared pipeline. The pipeline code (capture, draft, review, submit, audit) is written once; a feature supplies five things.

**What a feature module declares**

| Piece | Lives in | What it is |
| --- | --- | --- |
| Procore schema | Backend | Go struct + JSON schema for the record's create payload, and the list of Procore lookup endpoints it may reference (users, locations, spec sections, cost codes, vendors, drawings) |
| Extraction prompt + tools | Backend | System prompt for the record type, the LLM tool definitions bound to those lookups, and the structured-output schema (fields + `unresolved[]` + `confidence`) |
| Submit job | Backend | Idempotent job: upload attachments → create record → store Procore ID → emit audit row |
| Capture config | iOS | Which inputs the capture screen shows (voice, photos, location, free text) and any record-specific prompts ("which trade?") |
| Review screen | iOS | SwiftUI form bound to the generated draft type; pickers backed by `/lookups/{kind}`; flagged fields highlighted |

**Shared pipeline (never changes per feature)**

1. Capture screen records audio, transcribes on device, collects photos, stamps GPS/time, saves a local `Draft` (SwiftData).
2. `POST /v1/drafts` with `{feature, project_id, transcript, attachment_refs[]}`. Backend runs the feature's extraction, returns a `DraftResponse` with the typed payload, `unresolved[]` (field, candidates\[\], reason) and per-field `confidence`.
3. Review screen renders the payload; `unresolved` fields open their picker on first tap; user edits are diffed against the LLM output and stored.
4. `POST /v1/drafts/{id}/submit` with `Idempotency-Key`. Backend enqueues the feature's submit job and returns `202` with a job ID; app polls `GET /v1/jobs/{id}` or receives a push.
5. Audit row written: transcript, LLM output, user diff, final payload, Procore response, timings, model version.

**Lookups are shared and cached.** `GET /v1/projects/{id}/lookups/{kind}` returns users, locations, spec sections, cost codes, vendors, drawings from Procore with a 10-minute server cache and ETag so the app can prefetch on project select and work offline from the last copy.

**Attachments are shared.** `POST /v1/attachments` accepts a photo, stores it in object storage, and returns a ref; the submit job pushes it to Procore's Direct File Upload endpoint and swaps the ref for a Procore `upload_id`. The same path serves RFIs, daily logs, observations and punch items.

**Adding a feature is therefore:** one Go package, one prompt file, one Swift feature folder, one OpenAPI schema block. The target is under two days of work per feature once the framework exists.

## Feature 1 — RFI by dictation

The user says something like: *"RFI for 118 West Illinois, third floor. Mechanical drawings show the duct going through the beam at grid C-4. Need the structural engineer to confirm we can core through. This is holding up rough-in. Cost impact unknown. Assign to Mike, due Friday."* The app returns a reviewable RFI in under 10 seconds.

**Field mapping** ([Procore RFI create reference](https://developers.procore.com/reference/rest/rfis?version=1.0))

| Procore field | Source | Resolution rule |
| --- | --- | --- |
| `subject` | Generated | ≤ 100 chars, states the question, no filler |
| `question.body` | Rewritten transcript | Clean RFI prose; original transcript appended under "Field notes" |
| `assignee_ids`, `rfi_manager_id`, `distribution_ids` | `list_users` tool | Fuzzy match on name/role; ambiguous → `unresolved` with candidates |
| `responsible_contractor_id` | `list_vendors` tool | Match on trade or company name |
| `location_id` | `list_locations` tool | Match against the project's location tree ("third floor") |
| `specification_section_id` | `list_spec_sections` tool | Match on division or title ("mechanical" → 23 xx xx) |
| `drawing_number` | `list_drawings` tool or literal | Accept literal like "M-301"; else match drawing title |
| `cost_code_id` | `list_cost_codes` tool | Only when stated; never guessed |
| `due_date` | Parsed | Relative dates resolved in project timezone; default = project RFI default days |
| `schedule_impact`, `cost_impact` | Parsed | `{status: yes_known / yes_unknown / no / tbd, value}` from phrases like "holding up", "cost unknown" |
| `private` | Default `false` | Set `true` only if the user says so |
| `draft` | Default per user setting | New users default to `true` |
| `question.upload_ids` | Attachments | From Direct File Upload (below) |

**Submit job**

1. For each attachment: `POST /rest/v1.0/projects/{id}/uploads` → presigned S3 URL + upload UUID; PUT the file; collect `upload_ids`. Photos are downscaled to ≤ 2,500 px long edge and EXIF-stripped except orientation and GPS.
2. `POST /rest/v1.0/projects/{id}/rfis?run_configurable_validations=true` with the reviewed payload, so project-level required fields fail with a field-level error instead of creating an incomplete RFI.
3. On `201`: store the Procore RFI ID and number; return a deep link to the RFI in Procore.
4. On `422`: map Procore's field errors back to draft fields; return to the review screen with those fields flagged.
5. Idempotency: the job key is the draft ID; a retried submit after a network drop finds the stored Procore ID and does not post twice.

**Acceptance tests**

- Dictation with an unambiguous assignee, location and due date produces a payload with zero `unresolved` fields.
- "Assign to Mike" with two Mikes on the project produces `unresolved.assignee_ids` with both candidates.
- Submitting with no signal queues the draft; it posts within 30 seconds of connectivity returning, exactly once.
- A user with Read-only on the RFI tool is told so before recording, not after.
- Procore's configurable required fields trigger a field-level error on the review screen.

## Feature roadmap

Features ship one at a time in this order; each reuses the pipeline and adds only its module. Order is by field value and by how little new Procore surface each one needs.

| # | Feature | Procore endpoint | New lookups | What the user dictates | Notes |
| --- | --- | --- | --- | --- | --- |
| 1 | RFI | `POST /projects/{id}/rfis` | users, locations, spec sections, cost codes, vendors, drawings | Question, who, where, when, impacts | v1 |
| 2 | Observation | `POST /projects/{id}/observations/items` | observation types, trades | Issue, type (safety/quality), assignee, due | Smallest delta; same attachments path |
| 3 | Punch item | `POST /projects/{id}/punch_items` | punch item types, assignees, final approver | Deficiency, location, responsible party | Batch mode: walk a floor and dictate many items; LLM splits one recording into N items |
| 4 | Daily log — manpower, notes, weather | `POST /projects/{id}/daily_logs/{type}` (several sub-resources) | vendors, cost codes | "Had 6 electricians from ABC today, poured slab, rain stopped us at 2" | One recording → several log entries; weather can be auto-filled from a weather API |
| 5 | Photo upload with tagging | `POST /projects/{id}/images` + albums | albums, locations | Caption and location per photo | Lets a photo dump become organized Procore images |
| 6 | Submittal (create draft) | `POST /projects/{id}/submittals` | spec sections, responsible contractor | Spec, what, who, dates | Lower field frequency; later |
| 7 | Read / ask | `GET` across RFIs, submittals, daily logs | — | "What RFIs are open on Illinois assigned to Mike?" | Read-only assistant; no submit job. Candidate for Procore's agentic/MCP surface when it matures |

**Gate for starting the next feature:** the previous one has been used on a real project for two weeks with no duplicate submissions and under 20% of drafts needing more than two field corrections (measured from the audit log).

## iOS app spec (`field-assistant-ios`)

The app is a thin capture-and-review client; it contains no Procore logic and no LLM calls.

**Stack**

- Swift 6, SwiftUI, strict concurrency; minimum iOS 17 (iOS 18 for on-device Speech improvements where available).
- `Speech` framework for on-device transcription (`requiresOnDeviceRecognition = true`); `AVFoundation` for recording; raw audio kept locally until submit succeeds, then deleted.
- `PhotosPicker` + `AVCaptureSession` for camera; `CoreLocation` for a single fix per capture.
- `ASWebAuthenticationSession` for sign-in; `Keychain` for the session token.
- `SwiftData` for drafts, attachments metadata and cached lookups; `BackgroundTasks` for the submit queue.
- `FieldAssistantAPI` Swift package generated from the backend's `openapi.yaml` (URLSession transport).
- Fastlane for TestFlight; Xcode Cloud or GitHub Actions for build/test.

**Project layout**

```
FieldAssistant/
  App/              entry, DI container, deep links
  Core/
    Auth/           sign-in, session refresh, reauth prompt
    Capture/        recorder, transcriber, photo capture, location
    Drafts/         SwiftData models, queue, sync
    Lookups/        cached pickers (users, locations, spec sections…)
    Review/         generic form components, unresolved-field UI
    Network/        API client wrapper, idempotency, retry
  Features/
    RFI/            RFIReviewView, RFI capture config
    Observation/    (added later)
  Packages/
    FieldAssistantAPI/  generated client, pinned by tag
```

**Screens**

1. Sign in → company/project picker (remembers last; one-tap switch).
2. Home: big record button, feature chooser (only features the user has permission for), list of recent drafts with status chips (Draft / Queued / Submitted / Failed).
3. Capture: live transcript as the user speaks, photo strip, stop → "Build RFI". Works fully offline.
4. Review: prefilled form; unresolved fields shown amber with a picker; original transcript collapsible at the bottom; Submit as draft / Submit.
5. Result: Procore number, link to open in Procore, "New RFI" shortcut.
6. Settings: default draft behaviour, photo size, sign out.

**Offline and queue behaviour**

- Capture and transcription never need network.
- Draft extraction needs network; if absent the draft is saved as "Needs connection" and retried automatically.
- Submits carry a client-generated `Idempotency-Key` (the draft UUID) and are retried with exponential backoff from a `BGProcessingTask`; status is reconciled from `GET /v1/jobs/{id}`.
- Lookups are prefetched when a project is selected and refreshed on ETag mismatch.

**Accessibility and field use**

- Large tap targets, works with gloves; VoiceOver labels on every control.
- Speech runs in English first; the backend prompt is language-agnostic for later Spanish support.

## Desktop web app spec (`field-assistant-web`)

The desktop client is a web app on Cloudflare Pages that runs the same capture → extract → review → submit loop against the same backend; it adds nothing the phone cannot do, it just does it at a desk with a keyboard and a bigger screen.

**Why web rather than a native Mac app**

- Runs on macOS and Windows with one codebase and no installer; the office and the trailer PC both work.
- Deploys on every merge; no App Store cycle for desktop changes.
- The backend is unchanged: same OAuth broker, same drafts and jobs API, same generated contract.
- Native Mac via SwiftUI multiplatform would reuse iOS code but excludes Windows and cannot be hosted on Cloudflare; revisit only if desktop needs native audio or filesystem access.

**Stack**

- Vite + React + TypeScript; TanStack Query for data; generated client from `openapi-typescript` + `openapi-fetch`.
- Dictation: `MediaRecorder` captures audio; transcription uses the browser's Web Speech API where available (Chrome, Edge) with a backend fallback endpoint `POST /v1/transcribe` for browsers without it. Typing or pasting notes is a first-class input on desktop.
- Photos: drag-and-drop or file picker; the same `POST /v1/attachments` path.
- Sign-in: the backend's `/auth/start` redirect flow with the session held in an `HttpOnly`, `SameSite=Lax` cookie scoped to the API domain (the web app never sees a token). The iOS app keeps its JWT-in-Keychain path; both are issued by the same broker.
- Offline: not a goal for desktop; drafts are saved server-side as they are edited.

**Screens** mirror iOS: project picker, home with recent drafts, capture (record or type, drop photos), review, result. Batch mode for punch items (feature 3) is desktop-first: paste or dictate a walk-through and review the split list in a table.

**Layout**

```
src/
  app/            routes, auth guard, API client
  core/           capture (recorder, transcriber), attachments, lookups, review components
  features/
    rfi/          RfiReview.tsx, capture config
  api/            generated types + client, pinned by tag
```

## Backend spec (`field-assistant-api`)

A single Go service with Postgres and object storage; no microservices. It is the only thing that holds Procore credentials or calls an LLM.

**Stack**

- Go 1.23+, `chi` router, `oapi-codegen` server from `openapi.yaml`, `sqlc` for queries, `golang-migrate`.
- Postgres 16 (users, sessions, tokens, drafts, jobs, audit). Object storage: S3-compatible (R2 or S3) for attachments.
- Job queue: River (Postgres-backed) so there is no second datastore; workers run in the same binary.
- LLM: Claude API via the official Go SDK; tool use + JSON-schema output. Model per task configured, not hard-coded.
- Deploy: single Docker image on a DigitalOcean droplet behind Caddy, with Managed Postgres and Spaces (see Hosting and infrastructure).
- Observability: structured logs (slog), OpenTelemetry traces per draft and job, Prometheus metrics.

**Module layout**

```
cmd/api/                  main: http server + workers
internal/
  auth/                   OAuth broker, session JWT, token vault
  procore/                typed client: companies, projects, users, locations,
                          spec sections, cost codes, vendors, drawings, uploads, rfis…
                          rate-limit aware, retries, Procore-Company-Id injection
  llm/                    provider wrapper, tool dispatch, schema validation, prompt registry
  pipeline/               drafts, lookups cache, attachments, submit orchestration, audit
  features/
    rfi/                  schema.go, prompt.md, extract.go, submit.go, tests
    observation/          (later)
  jobs/                   River workers: submit, attachment push, token refresh
  store/                  sqlc queries, migrations
api/openapi.yaml          the contract
```

**Data model (core tables)**

| Table | Key columns |
| --- | --- |
| `users` | id, procore\_user\_id, company\_id, email, created\_at, reauth\_required |
| `procore_tokens` | user\_id, refresh\_token\_enc, access\_token\_enc, expires\_at, updated\_at |
| `sessions` | id, user\_id, refresh\_hash, expires\_at, device\_id |
| `drafts` | id (client UUID), user\_id, company\_id, project\_id, feature, transcript, llm\_output jsonb, user\_payload jsonb, status, model\_version |
| `attachments` | id, draft\_id, object\_key, mime, bytes, procore\_upload\_id |
| `jobs` | River-managed; `kind`, `args`, `state` |
| `audit_events` | draft\_id, kind (extracted / edited / submitted / failed), payload jsonb, procore\_response jsonb, at |
| `lookup_cache` | company\_id, project\_id, kind, etag, body jsonb, fetched\_at |

**API surface (v1)**

| Method + path | Purpose |
| --- | --- |
| `POST /auth/start`, `GET /auth/callback`, `POST /auth/refresh`, `POST /auth/logout` | Sign-in broker and app sessions |
| `GET /me`, `GET /companies`, `GET /companies/{id}/projects` | Scope selection |
| `GET /projects/{id}/features` | Features and permission state for this user on this project |
| `GET /projects/{id}/lookups/{kind}` | Cached Procore reference data with ETag |
| `POST /attachments` | Upload a photo, get a ref |
| `POST /drafts`, `GET /drafts/{id}`, `PATCH /drafts/{id}` | Create via extraction; read; save user edits |

| `GET /drafts` | Recent drafts for the home screen |

**Procore client rules**

- Respect Procore rate-limit headers; back off on 429.
- All list calls paginate fully before caching.
- Sandbox base URL switchable per environment; integration tests run against the monthly sandbox.

## LLM design

The model fills a schema from a transcript; it is never allowed to invent an identifier, and everything it produces is reviewed by a person before it reaches Procore.

**Extraction call**

- Input: feature system prompt, project context (name, timezone, today's date, default RFI due days), the transcript, photo captions if a vision pass ran, and the feature's tool set.
- Tools (read-only, bound to the lookup cache): `list_users(query?)`, `list_locations(query?)`, `list_spec_sections(query?)`, `list_cost_codes(query?)`, `list_vendors(query?)`, `list_drawings(query?)`. Each returns `{id, label, extra}` rows; the model must cite an `id` from a tool result for any ID field.
- Output: structured JSON matching the feature schema plus `unresolved: [{field, reason, candidates: [{id, label}]}]` and `confidence: {field: 0–1}`. The backend validates every ID against the lookup cache and demotes any unmatched ID to `unresolved` regardless of what the model said.
- Budget: one extraction should complete in under 8 seconds and under 6 tool calls; the lookup cache makes tool calls sub-100 ms.

**Model selection**

| Task | Model class | Why |
| --- | --- | --- |
| Extraction (transcript → schema) | Sonnet-class | Best cost/accuracy for tool use + structured output |
| Photo captions | Haiku-class with vision | Cheap, many images |
| Batch split (one recording → many punch items) | Sonnet-class | Needs careful segmentation |
| Read/ask assistant (feature 7) | Sonnet- or Opus-class | Multi-step reasoning over several Procore reads |

Model IDs live in config and are recorded on every draft (`model_version`) so behaviour changes can be traced.

**Prompt rules**

- Write RFI prose in the house style: question first, context second, what is blocked third; no hedging language.
- Keep every proper noun from the transcript unless it was resolved to an ID.
- Relative dates resolve against the project timezone; ambiguous dates become `unresolved`.
- Never set `cost_impact.value` unless a number was spoken.
- Prompts are versioned files under `features/<name>/prompt.md`; a change requires the eval set to pass.

**Evals**

- Golden set: 50 real or realistic transcripts per feature with expected payloads, built from the audit log (user-corrected payloads become new cases).
- Metrics: field exact-match rate, ID hallucination rate (must be 0 after validation), unresolved precision (flagged fields that the user actually changed), latency p95.
- Run on every prompt or model change in CI against the sandbox lookup fixtures.

**Privacy**

- Transcripts and photos go to the LLM provider under a zero-data-retention agreement where available; no customer data is used for training.
- Audio never leaves the device.

## Security, audit and Procore platform

**Secrets and tokens**

- Procore `client_secret`, LLM API key and the token-vault key exist only in the backend's secret store; never in the repo, CI logs or the app.
- Refresh tokens are envelope-encrypted per row; the data key is rotated quarterly.
- App sessions are short-lived JWTs with refresh rotation; a reused refresh token invalidates the whole session family.
- Certificate pinning to the backend host in the iOS app.

**Audit**

- Every draft stores transcript, LLM output, user diff, final payload, Procore request/response and timings. Retention 2 years, configurable per company.
- An admin export (`GET /admin/audit?company=…`) produces CSV for a date range.

**Procore Developer Portal**

- One app registration with production and sandbox credentials; the sandbox is used for all automated tests.
- Request the minimum permission scope; document per feature which Procore tools it touches.
- Marketplace listing (optional, later) requires Procore's app review, a published privacy policy, and support contact; building multi-tenant from the start keeps this door open.
- Procore has begun advertising an agentic app surface (an MCP server component declared in an app manifest). Revisit for feature 7 (read/ask); not needed for record creation.

**App Store**

- Privacy manifest declaring microphone, camera, photos and location use with purpose strings.
- No account creation inside the app (sign-in is Procore's), which simplifies review.

**Phase exit criteria**

1. Auth, contract, repos — a user signs in on the phone, picks a project, sees their RFI list from the backend; `openapi.yaml` generates both the Go server and the Swift client in CI.
2. RFI extract + review — a dictated RFI becomes a reviewable draft with resolved IDs and posts to the sandbox without attachments.
3. Photos, uploads, offline — attachments reach Procore via Direct File Upload; a submit with no signal completes exactly once when connectivity returns.
4. Hardening — permission errors, token revocation, configurable validations, audit export; first build to the 118 W Illinois team.
5. Site pilot — daily use on one project; audit log reviewed weekly; eval set seeded from corrections.
